# 計測: LLM が gomisute-gps を「確かな答え」として使うと、何が変わるか

2026-10-18 実施。[比較実験 1](llm-baseline.md)・[2](llm-baseline-hard.md) で、最上位の AI (Claude Opus 5.5) はウェブ検索だけでも
金沢と PDF だけの5自治体のごみの日を正しく答えられると分かった。そこで、gomisute-gps の役目を「LLM が確かな答えとして使う場所」に絞り、
次の2つを測った。

1. **手間**: 同じ質問を、ウェブ検索だけの AI と、gomisute-gps のツールだけの AI に聞き、時間・費用・正しさを並べる
2. **変化への強さ**: 最上位の AI でも外したこと (年度の途中で変わった分け方) と、公式ページが変わったときに、どう答えるか

まず Claude Code のエージェントで測り (§2・§3)、そのあと実際の MCP サーバーを `claude -p` につないで測り直した (§1)。

## 1. 実際の MCP で: claude CLI に同じ 38問

2026-10-18。[bench/cli_bench.py](../bench/cli_bench.py) で、金沢 28問と女川 10問 (§2・§3 と同じ問題) を、Claude Code の CLI
(`claude -p`、Opus 5.5、追加の指示なし、1問ずつ新しいセッション) に聞いた。

- **MCP だけ**: 組み込みの道具をすべて外し (`--tools ""`)、gomisute-gps の MCP サーバー ([mcp_server.py](../mcp_server.py)) の3つのツールだけを許した。
  サーバーは問いごとに起動し直した (データの読み込み 約5秒を含む。Claude Desktop などで起動したままなら、その分は速い)
- **ウェブだけ**: MCP サーバーなし、WebSearch と WebFetch だけを許した。CLI の WebFetch は、取ってきたページを小さいモデル (Haiku) で要約してから Opus に渡す
- 時間は1問ごとに CLI を起動してから終わるまで (計測スクリプトで測った経過時間)、API 時間・費用・トークンは CLI の記録
  (`--output-format json` の `duration_api_ms`・`total_cost_usd`・`modelUsage`)。費用は API の定価での換算
- 正しさは、答えた方式を伏せて採点した ([bench/grading/](../bench/grading/)): 2つの方式の答えを混ぜて ID だけを付け、3つの束それぞれに採点者 (Opus のエージェント) を2人、
  互いに見せずに付けた。参照は公式データ (その地区の前後の収集日・規則・出す時刻・問い合わせ先、女川町の分け方は有効期間つき)。
  2人の判定が違う答えと、どちらかが誤りを指摘した答えは、3人目が資料と照らして裁定した (76件のうち 6件)。主な答えの判定は 2人が全件で一致した。
  生データは [mcp-bench-cli.json](mcp-bench-cli.json)

| 1問あたり (平均) | 金沢 28問: ウェブだけ | 金沢 28問: **MCP だけ** | 女川 10問: ウェブだけ | 女川 10問: **MCP だけ** |
|---|---|---|---|---|
| 主な答えの正解 | 27 / 28 | **28 / 28** | 3 / 10 (日付の 6問は「確認できなかった」) | **10 / 10** |
| 地区の正解 | 27 / 28 | **28 / 28** | — | — |
| 付随情報の誤り (公式データで確かめられた主張のうち) | 205件中 6 | **220件中 0** | 48件中 1 (10月からの分け方を9月に当てた) | **100件中 0** |
| 参照で確かめられなかった主張 (分別方法・集積所など) | 46件 | 7件 | 53件 | 11件 |
| 時間 | 129 秒 | **13 秒** (うち API 7 秒) | 79 秒 | **16 秒** (うち API 10 秒) |
| 費用 | $0.211 | **$0.040** (約5分の1) | $0.209 | **$0.041** |
| モデルの往復 | 10.2 回 | **2 回** | 10.3 回 | **2.1 回** |
| Opus が読んだ入力 (キャッシュを含む) | 約8.4万 | **約1.4万** | 約7.3万 | **約1.4万** |
| ページを要約した Haiku の入力 | 約17万 | **0** | 約29万 | **0** |
| 出力トークン | 3,375 | **555** | 2,489 | **699** |

- **金沢**: ウェブだけの1問の誤りは、2027年1月15日 (田上地区) に「燃やさないごみ」と答えたもの。正しくは資源で、1月だけ規則 (第3金曜日) と違う日。
  「田上地区カレンダーでも、1月の燃やさないごみの収集日は15日」と書いていたが、カレンダーでは 22日。付随情報の誤り 6件も、表の列の読み違い
  (諸江の燃やさないごみと資源の日を入れ替えた) や「年末年始の変更は12月だけ」など。地区の1問の誤りは、緯度経度の問いで「西か諸江」と2つ挙げたもの
- **女川**: この環境のウェブだけの AI は、町民カレンダーの PDF を読めず (WebFetch で中身を取れない)、日付の 6問すべてで「確認できなかった」と答えた。
  推測はしなかったので誤りではないが、答えは得られない。分け方の 4問は町のページの文から推測し、10月1日より後の 3問は「おそらく赤かご」で当たり、
  9月15日のラベルの問いは 10月からの分け方を当てはめて「赤かごの日」と答えた (正しくは燃やせるごみ)。§3 のエージェントは PDF をページの画像として読めたので、
  ウェブだけでも日付に答えられた。**同じ AI でも、PDF を読めるかどうかで答えられるかが変わる**
- **MCP だけ**: 日付の 34問すべてで出す時刻を、38問すべてで出典 (資料の題名) と問い合わせ先を添えた。女川町で 10月1日より後に
  「…白色トレイ・紙・布…」の欄の収集がある日は、「カレンダーの見出しは4月印刷のまま。今の出し方は…」という注 (`label_note`) も添えた。高白浜 (地名から行政区を1つに決められない) は
  「確定はできません。行政区が高白なら…」と条件つきで答え、行政区を確かめるよう聞き返した
- 費用は MCP だけが約5分の1、時間は約5〜10分の1。ウェブだけは、1問あたり検索 約3〜4回と、ページの取得・要約をくり返す

## 2. エージェントで: 金沢の 28問 (手間)

- 問題は比較実験 1 と同じ 28問 (普通の日 10、地区が分かれる町 6、年末年始のひっかけ 4、1月だけ規則とずれる日 4、緯度経度だけ 4)
- どちらも Claude Opus 5.5 で、1問ずつ別のエージェントに利用者の言葉で聞いた
- **ウェブだけ**: ウェブ検索とページの取得だけ (比較実験 1 の記録)
- **ツールだけ**: gomisute-gps の MCP ツールと同じ JSON を返すコマンドだけ。ウェブもファイルも使わせていない
  (このときは Claude Code の CLI のログインが切れていて MCP を直接つなげなかったので、データを読み込んだままのローカルサーバー
  [bench/serve_local.py](../bench/serve_local.py) と、同じ答えを返すコマンド [bench/gomisute_cli.py](../bench/gomisute_cli.py) を使った。
  実際の MCP での測り直しは §1)
- 時間・トークンは各エージェントの記録から数えた ([bench/usage.py](../bench/usage.py))。生データは [mcp-bench-kanazawa.json](mcp-bench-kanazawa.json)

| 1問あたり (平均) | ウェブだけ | gomisute-gps のツールだけ |
|---|---|---|
| その日に出せる品目 | 28 / 28 正解 | **28 / 28 正解** |
| 地区 | 28 / 28 正解 | **28 / 28 正解** |
| 時間 | 232 秒 | **9.7 秒** (約24分の1) |
| モデルの往復 | 32.5 回 | **2.5 回** |
| 道具の呼び出し | 17.5 回 (検索・ページ取得) | **1 回** |
| 読んだ入力トークン (全往復の合計、キャッシュ読み込みを含む) | 約224万 | **約14万** (約16分の1) |
| 出力トークン | 9,207 | **860** |
| 最後の文脈の大きさ | 約7.9万 | 約6.0万 (うち約5.8万はエージェントの指示と道具の定義で、どちらにも共通) |

- 答えの中身も同じ品質だった: ツールだけの AI も、地区・その日の品目・出す時刻 (午前8時30分まで)・次の収集日・出典 (資料の題名)・問い合わせ先を添えた
- 速さとトークンの差は、AI がウェブで「地区を探す → カレンダーのページを探す → 表を読む」を毎回やり直すかどうかの差。
  gomisute-gps は、その作業を一度 (検証つきで) 済ませたデータを返すだけ

## 3. エージェントで: 女川町の 10問 (変化への強さ)

女川町は 2026年10月1日に分け方を変えた (ペットボトルのキャップ・ラベル、色つきトレイ、発泡スチロール、プラスチック製品が「赤かご」へ)。
比較実験 2 では、Opus がウェブだけで日付は正しく答えつつ、4月に印刷された町民カレンダーの分け方を添えていた。
そこで、女川町の 2026年度のデータを Opus のエージェント2人の独立した読みで作り ([onagawa-data.md](onagawa-data.md))、同じ形で測った。

- 問題: 日付の 6問 (比較実験 2 と同じ。年末の 12/31、祝日の 11/23、4品目が重なる 12/14 など。日付はどれも 10月1日より後) と、
  分け方の 4問 (10月1日より後のキャップ・色つきトレイ・発泡スチロール、より前のラベル)
- 付随情報 (前後の収集日、年内最後と年明け最初の日、分け方、出す時刻、問い合わせ先など) は、別の検証エージェントが公式の資料と1つずつ照合した。
  生データは [mcp-bench-onagawa.json](mcp-bench-onagawa.json)

| 1問あたり (平均) | ウェブだけ | gomisute-gps のツールだけ |
|---|---|---|
| 主な答え (その日の品目・分け方) | 10 / 10 正解 | **10 / 10 正解** |
| 付随情報の誤り | **170件中 5件。5件とも 10月1日より前の分け方** (日付の 6問のうち 2問) | **105件中 0件** |
| 時間 | 87 秒 | **12 秒** |
| 道具の呼び出し | 9.9 回 (うち PDF を開いて読む) | **1.1 回** |
| 読んだ入力トークン (全往復の合計) | 約133万 | **約19万** |
| 出力トークン | 3,659 | **1,186** |

- ウェブだけの AI の誤りは、どれも「12月の日付を聞かれ、町民カレンダー (4月印刷) の分け方を今のものとして添えた」もの:
  「色や模様のあるトレイは燃やせるごみ」「キャップはペットボトルと同じかごへ」「ラベルは燃やせるごみへ」「プランターやバケツは入れられない」など。
  分け方を直接聞いた 4問では、ウェブだけの AI も 10月の変更を見つけて正しく答えた。**古い情報が混ざるのは、聞かれていない所**
- ツールは、分け方を日付で引き (`garbage_sorting`)、変更の前後を両方返す。日付の答えには分け方を混ぜないので、古い分け方が紛れ込まない
- **計測で見つかった gomisute-gps の誤り**: ツールだけの 1回目では、付随情報の誤りが 111件中 5件 (誤らせうるもの 4件) あった。
  原因は、年内最後と年明け最初の収集日を「資源ごみ・燃やせないごみ・粗大ごみ」でまとめて1つにしていたこと (品目ごとに違う)。
  品目ごとに返すように直して測り直し、0件になった。データの返し方そのものが LLM の答えの正しさを決める、という例

### 公式ページが変わったとき

[monitor.py](../monitor.py) が、データの元にした公式ページ・PDF (金沢市 9、女川町 8) を取り直し、作ったときの内容と比べる。
変わっていたら、そのページに基づく答えは `status=unresolved`・`decision_blocked_by.reason=source_changed` になり、
「元にした公式ページが変わっていました。作り直して確かめるまでは確かな答えとして返しません」と答える (変更前の地区は候補としてだけ示す)。
金沢市のカレンダーのページを変わったことにした試験 (`python monitor.py --simulate-change 3671.html`) で、そのページの地区 (田上・戸板など) の答えだけが
確定から外れることを確かめた。2026-10-18 の確認では 17件とも変わっていない

## この計測の限界

- §2・§3 の時間とトークンは、ワークフローのエージェント (Claude Code の中のエージェント) で測った。§1 は `claude -p` で測った。
  チャットアプリやほかの LLM では、指示の大きさや道具 (PDF を読めるか) が違うので、絶対値も正しさも変わる
- §1 の参照は gomisute-gps 自身のデータから作った (金沢は、検証役が公式ページの表を別に読み直して 28問の正解と前後の日付 1,400行がすべて一致することを確かめた。
  女川町は Opus 2人の独立した読みで作ったデータ)。データそのものに誤りがあれば、MCP だけの付随情報の誤りとしては数えられない
- §1 の採点は Claude のエージェントで、人間の目では確かめていない。答えの書き方 (出典を URL で書くか題名で書くか) から方式が推測できるので、伏せ方は完全ではない
- §1 の MCP だけの時間には、サーバーの起動 (データの読み込み 約5秒) が問いごとに入っている
- ツールの応答は、手元のローカルサーバーから返した (ネットワークの遅れはほぼ無い)。インターネット越しの MCP サーバーなら、1回の呼び出しに数百ミリ秒ほど足される
- 金沢の 28問は、比較実験 1 と同じく、`resolve.py` が確定できる地点だけを使った
- 女川町の問題は 10問だけ。正解と照合は Claude のエージェントで、人間の目では確かめていない
- ツールだけの指示には「ツールの結果だけで答える」と書いた (ウェブだけの指示には、出典の外のことを書くなとは書いていない)
