# 先行事例: address2houmukyoku から引き継ぐもの

調査日は 2026-10-17 です。対象リポジトリは読み取りだけで、変更していません。

この文書では、事実と推奨を分けて書きます。

- **【事実】** 2 つのリポジトリで確認したことです。ファイルパスは、特に断りがなければ address2houmukyoku 内のものです。
- **【推奨】** gomisute-gps 側への提案です。どちらのリポジトリにもまだ実装されていません。
- **(計測)** 付きの数値は、調査セッションで一時的に書いたスクリプトで、実データに対して数えたものです。そのスクリプトはどちらのリポジトリにもコミットしていないので、使う前に再現してください。

## 1. 位置づけ

**【事実】** address2houmukyoku は、住所の文字列を受け取って、管轄する法務局を返すサービスです。不動産登記と法人登記の両方の管轄を返します。

- 作者は gomisute-gps と同じで、別プロジェクトです。リポジトリは**非公開**です。
- 構成は Cloudflare Worker と Hono です。デプロイ時のエントリは `server.ts`(ルート)です。
- 照合に使うデータは 2 つです。
  - `data/houmukyoku.json`: 1,832 行、47 都道府県、市区町村は 1,815 組。lastUpdated は 2026-05-08。
  - `data/municipality-aliases.json`: 1,801 件。lastUpdated は 2026-05-05。
- 法務局サイトの管轄表(50 ページ)を LLM で構造化したものが、照合データの元になっています。
- 回帰検証では、日本郵便の KEN_ALL 124,822 行を検索にかけ、「実用一致 100%」と報告しています(`data/verify-summary.json`)。

**【事実】** gomisute-gps 側の方針は、HANDOFF.md の 2026-10-16 の「追加決定」にあります。address2houmukyoku は「流用元」で、拡張はしません。新しく作る address-normalize Worker の L1(市区町村層)で、旧市町村対応表を共有する計画です(docs/address-normalize-schema.md)。

gomisute-gps が受け取るもの・受け取らないものは次のとおりです。

| 受け取る | 受け取らない |
|---|---|
| 旧市町村→現市町村の対応データ(加工してから使う。§2) | コード(非公開のため。§7) |
| 正規化の規則とその例外(§3) | 部分文字列スコアリングによる検索アルゴリズム |
| 回帰検証の骨格: スナップショット・ベースライン・終了コード(§4) | 法務局固有の行の粒度(政令市を区単位で持つか市単位で持つか、など) |
| ハッシュ差分で LLM を再抽出するパイプライン(§5) | `[site]` バケットを使うデプロイ構成 |
| 特殊分割の分類(§6) | |

## 2. 共有するデータ: municipality-aliases.json

### 2.1 形と件数【事実】

- **形**: `{lastUpdated, aliases: {old_full: {old_full, new_full, date, type}}}`。キーは old_full で、1 件の旧名に後継は 1 つだけです。このため、1 つの旧市町村が複数の後継に分かれる「分割」は表現できません。
- **件数**: 1,801 件です。
  - type の内訳: 合併 1,676 / 市制施行 114 / 区設置 10 / 名称変更 1
  - new_full の種類は 606
- **期間**: 1986-03-01 から 2019-05-01 まで。年別の山は 2004 年 307 件、2005 年 863 件、2006 年 361 件です。
  - 最も新しい 2 件は、2018-10-01 の那珂川町→那珂川市と、2019-05-01 の篠山市→丹波篠山市です。
  - README.md には「1985年以降」とありますが、実データは 1986-03 から始まります。
- **表記**: キーのうち 11 件が「ヶ」を含み、「ケ」を含むものは 0 件です。
- **出典情報**: 行ごとの出典 URL や根拠は持っていません。

### 2.2 作り方(LLM 抽出と検証)【事実】

**抽出**: `scripts/build-aliases.ts` が、都道府県ごとに 1 回(計 47 回)LLM に問い合わせます。

- 尋ねる内容は「1985年以降の市制施行・合併/編入・名称変更・区設置」です。
- 出力は JSON Schema で形を強制しています。日付は YYYY-MM-DD、type は 4 値の列挙です。
- 指示の要点は 3 つです。
  - N:1 の合併は、旧市町村 1 つにつき 1 件にする
  - 旧市町村が複数の区にまたがるときは、最大の区を代表にする
  - 不確かなものは出力しない
- キャッシュは `.cache/aliases/<都道府県>.json` です。ハッシュも有効期限もなく、一度作ると再利用され続けます。

**補正**: `scripts/fix-aliases.ts` は、LLM の生出力には手を付けず、別の工程で補正します。

- 16 件の上書き表を適用します。この表から、LLM がよく間違える型がわかります。
  - 改称の見落とし(篠山→丹波篠山)
  - その後の再編入の見落とし(浜北市→浜松市)
  - 中間状態を後継にしてしまう(豊見城町→豊見城市)
  - 存在しない市を作る(清武市)
  - 郡を間違える
- その後、次の処理をこの順で行います。
  1. ケ/ヶ の表記を houmukyoku.json の表記にそろえる
  2. old と new が同じものを除く
  3. 「X市Y区」を「X市」に落とす(法務局データが市単位で持つ政令市の場合)
- **検証**は「new_full が houmukyoku.json に存在する」ことだけです。弾いた行は標準出力に出るだけで、保存されません。
- (計測)この補正を再実行すると、生出力 1,851 件から 1,801 件になり、コミット済みファイルとバイト単位で一致しました。

### 2.4 2019 年以降の空白と、ABR mt_city で埋める方法

**【事実】** ABR の mt_city は履歴を持っていません。

- 1,918 行のすべてで ablt_date(廃止日)が空です。
- efct_date(効力発生日)は 1,915 行が 1947-04-17 の仮置きです。
- 実際の日付が入っているのは 3 行だけで、2024-01-01 の浜松市 中央区 221384 / 浜名区 221392 / 天竜区 221406 です。2024 年より前の浜松市の 7 区は載っていません。
- mt_city の区以外の行は 1,747 行です。1,741 市区町村に北方領土の 6 村(016951〜017001)を加えた数です。
- aliases には、浜松市の 2024-01-01 の区再編が入っていません。浜松の 12 件は、旧区ではなく新しい 3 区に対応づけ直す必要があります。

**【推奨】** mt_city を毎月スナップショットし、前月との差分を取ります。

- 差分の対象は 2 つです。lg_code が現れたか消えたか、そして仮置きでない efct_date が付いたかです。
- 差分から muni_alias の候補イベントを作ります。
- 旧→新の対応と日付は、調査用エージェントと反証用エージェントで埋めます。

市区町村の数は 2014 年から 1,741 のままです。そのため L1 で今後起きる変化は、主に区の再編・市制施行・改称だと見込まれます。出典を示せる形で過去分を埋めるには、総務省の全国地方公共団体コードの改正一覧を当たるのが有力です(未検証)。

### 2.5 L1 muni_alias への取り込み手順【推奨】

1. **alias_full**: old_full を生の表記のまま入れます。**alias_key** は、gomisute-gps 自身の norm_rule で計算し直します。address2houmukyoku が作ったキー(ヶ 寄せ)は使いません。
2. **lg_code**: new_full を mt_city に突き合わせて決めます。まず生の表記で照合し、だめなら照合キーで照合します。
   - 下呂の 5 件は、下呂市 212202 に寄せます。条件の文字列は evidence に残します。
   - 政令市の親を指す 45 件は、親の lg_code(例: 新潟市 151009)と「区は未確定」の印で入れます。区は、L2 または gps2city が返す ward で決めます。旧市町村のポリゴンと現在の区を重ねて面積比を出すのは後回しにします。
3. **取り込まない行**: 現行の名前を old_full に持つ行は捨てます。区設置の自己写像は、どうしても残すなら「親 → 全区」の 1:N 行として作り直します。
4. **event / effective_date**: type と date をそのまま写します。ただし、old_full をキーにした写像ではなく、イベントの列として持ちます。静岡市の 合併 2003 と 区設置 2005 は両方残します。
5. **source と confidence**: source は `address2houmukyoku@2026-05-05T12:59:34.867Z` とします。confidence は 0.8 で始め、次の検査をすべて通った行だけ 1.0 にします。
   - 後継の lg_code が実在する
   - 旧名が現行名ではない
   - type と名前の形が合う(市制施行なら 町/村→市)
6. **CI**: 手順 3 と 5 の検査を CI で毎回回します。弾いた行は理由付きでファイルに保存します。

## 3. 正規化の知見

### 3.1 address2houmukyoku の規則【事実】

- **照合キーの中だけで畳みます。** 表示する文字列はデータのままです。
  - ケ→ヶ(小書きのほうへ寄せる)
  - 旧字→新字の 18 組: 惠→恵、德→徳、髙→高、﨑→崎、濱→浜、寳→宝、國→国、澤→沢、瀧→滝、圓→円、黑→黒、禮→礼、佛→仏、嵜→崎、薗→園、藏→蔵、榮→栄、齋→斎
- **意図的に畳まない文字**: 龍・嶋・灘・嶽・斎(README.md)。たとえば 茨城県鹿嶋市 と 佐賀県鹿島市 は別の市です。
- **規則の置き場所が 2 つあります。** `src/search.ts` と `scripts/verify/normalize.ts` に手作業で同じ規則を書いています。2 つが一致しているかを確かめるテストはありません。
- **文字数が変わらない畳み方だけを使っています。** そのため、「正規化した文字列で位置を探し、その位置で元の文字列を書き換える」という別名置換が成り立っています。
- **郡の扱い**
  - houmukyoku.json では、923 の町村が郡名付きで載っています。郡名が無いのは 10 だけです(愛荘町と、東京都の島しょ部 9 町村)。
  - 入力に余分な郡名や島名が付いていても照合できます。
  - 一方、都道府県があって郡名を省いた入力(例: 長野県軽井沢町)は、結果が空になります(計測)。
  - README.md が説明する「郡名/島名の吸収」は、検証側の比較関数にしかありません。
- **都道府県名どうしの部分一致**: 危険があるのは全国で「京都府 ⊂ 東京都府中市」の 1 件だけです(計測)。このバグはコミット eaa1759 で直っています。
- **同じ都道府県内で市名が包含関係になる組**: 7 組あります(大阪市⊂東大阪市 など)。最長一致で解決しています。

### 3.2 townnorm.py との向きの衝突と、解き方

| 規則 | address2houmukyoku | townnorm.py の現状 | 推奨の種別 |
|---|---|---|---|
| ヶ/ヵ/ケ | キーの中で ケ→ヶ | norm_town で ヶ,ヵ→ケ | key_only。ケ に寄せる(ヵ も扱える) |
| 嶽/岳 | 畳まない | norm_town で 嶽→岳 | key_only。候補はすべて返す |
| 舘薮刈 → 館藪苅 | 該当なし | norm_town | key_only |
| 之/の・ノ/の | 該当なし | 之 は norm_town、ノ は match_key | key_only |
| 旧字 18 組 | キーの中で畳む | 無し | key_only として追加し、since を付ける |
| 全角数字・空白・漢数字の丁目・「N丁」・末尾の数字→丁目 | 該当なし | norm_town | canonical(表示名も寄せる) |

**【事実】**

- townnorm.norm_town は、異体字の畳み込みを canonical 側(表示名と辞書のキーに使う関数)で行っています。スキーマ文書の「key_only」という分類と食い違っています。
- `lineage_report.py` は、`norm_town` の結果をキーにした辞書を作ります。キーが衝突すると、黙って上書きされます。
  - 金沢で衝突するのは 3 件(観音町3丁目・二宮町・二ツ屋町)です。どれも同じ machiaza_id が `rsdt_addr_flg` 0 と 1 で 2 行あるもので、別の町字どうしの衝突ではありません(2026-10-17 確認)。
  - 全国の ABR でも、(lg_code, machiaza_id) が重複するキーは 1,248 件(210 自治体)あり、すべてこの形です。住居表示と地番が混在する町字の表し方なので、取り込み時に 1 行にまとめる必要があります。

**【事実】(計測)** ABR の mt_town_fullset_all.csv(727,467 行)で、同じ lg_code の中で畳むと別の町字が衝突する組を数えました。

| 畳み込み | 大字・丁目の行だけ | 小字も含める |
|---|---|---|
| ケ/ヶ | 9 | 162 |
| ノ/の | 8 | 147 |
| 旧字 18 組 | 6 | 103 |
| 舘薮刈嶽 | 2 | 88 |
| 之/の | 0 | 6 |

ケ/ヶ と ノ/の を合わせた 17 は、スキーマ文書の「17件」と同じです。ケ/ヶ の衝突数は、どちらの向きに寄せても変わりません。

**【事実】** 公式の表記は、どの出典でも ケ と ヶ が混在しています。

- ABR には、ケ の 袖ケ浦市・鎌ケ谷市・保土ケ谷区 などと、ヶ の 茅ヶ崎市・駒ヶ根市 など 11 市町村の両方があります。
- 法務局データと ABR では 3 件の表記が食い違っています。七ケ宿町・七ケ浜町(法務局 ケ / ABR ヶ)と、保土ヶ谷区(法務局 ヶ / ABR ケ)です。

**【推奨】**

1. 表示するのは ABR の表記そのままにします。畳み込んだ文字列は保存しません。2 つのシステムの間で、生の文字列どうしを比べないでください。
2. 異体字の畳み込みを norm_town から match_key に移し、スキーマ文書の分類と合わせます。1 つのキーに複数の町字が当たったら、すべて返します。lineage_report.py の辞書は、上書きせずにリストで持つようにします。
3. 畳み込み規則は norm_rule テーブル 1 か所にまとめます。そこから JSON を出力し、Python と Worker(TS)の両方が読み込むようにします。規則集合のハッシュを確かめるテストを置き、すべての報告に rule_set_version を書きます。
4. 新しい規則を追加する前に、ABR で lg_code ごとの衝突を調べます。畳まない規則(龍・嶋 など)も、理由付きの行として明示的に持ちます。
5. 表示名を寄せる canonical の規則は、文字数を変えます(空白の除去、丁→丁目、漢数字の変換)。このため、正規化後の位置と元の位置の対応表を持つか、先にトークンに分けてください。別名のキーは、呼び出しのたびに正規化せず、あらかじめ計算しておきます。
6. 入力は前から順に読んで消費する方式で解析します(都道府県 → 郡(省略可)→ 市 → 区 → 町字)。文字列のどこかに含まれていれば一致、とはしません。部分文字列の検索は、印を付けた最後の手段に限ります。これで schema の `rest` も埋まります。
7. 郡のある 923 の町村は、郡あり・郡なしの 2 つのキーで索引します。島しょ部の町村は、島名付きの形(三宅島三宅村 など)でも索引します。入力に都道府県があれば候補をその都道府県に絞りますが、それ以外の照合を止めることはしません。

## 4. 回帰検証の設計と gomisute-gps への移植案

### 4.1 address2houmukyoku の仕組み【事実】

**流れ**(README.md の「1年後再実行のフロー」)

1. `scripts/verify/fetch-zipcodes.ts`: KEN_ALL を取得し、日付付きの NDJSON と `.meta.json` に保存します。meta の中身は {fetchedAt, sourceUrl, entryCount, zipBytes} です。
2. `scripts/fetch-houmukyoku.ts`: 法務局のページを取り直し、変わったページだけ LLM で抽出し直します。
3. `scripts/verify/check-html-drift.ts`: 法務局ページの特殊表記と、抽出済みデータを突き合わせます。
4. `scripts/verify/run.ts`: KEN_ALL の 124,822 行を検索にかけます。所要時間は約 10 秒です。
5. `scripts/verify/summarize.ts`: 結果を集計します。
6. `scripts/verify/diff.ts`: ベースラインと比べます。

**分類**は 9 種類です。

- 合格: EXACT / HOUMU_PREFIX / CSV_PREFIX / CSV_EXTRA_PREFIX / STEM_MATCH / MULTI_PARTIAL
- 失敗: PREF_MATCH / NOT_FOUND / PREF_MISMATCH

**2026-05-08 の結果**(`reports/verify-2026-05-08.json`): EXACT 118,602 件(95.02%)、HOUMU_PREFIX 6,165 件、CSV_EXTRA_PREFIX 55 件、失敗 0 件。

**ベースライン**: `data/baselines/verify-baseline.json` は {date, byZip: {郵便番号→失敗分類}} の形で、失敗だけを記録します。現在は空です。diff は失敗を 4 つに振り分けます(新規 / 解消 / 継続 / 分類変化)。終了コード 1 になるのは、新規の失敗があるときだけです。

**終了コードの規約**(README.md)

- 0: 問題なし
- 1: ベースライン比で新しい失敗がある(退行)
- 2: 法務局ページに新しい特殊表記が出たが、データに反映されていない

### 4.2 「100%」が意味しないこと【事実】

- 合格の条件は「返った候補のどれか 1 つが、同じ都道府県で、市区町村名の比較が mismatch 以外」であることだけです。答えが 1 つに決まっているかも、法務局の支局名も確かめていません。
- (計測)124,822 件のうち 642 件(0.51%)で、不動産登記の管轄が 2 つ以上返ります。
- KEN_ALL には現在の地名しかないため、1,801 件の別名は一度も使われません。別名を確かめているのは単体テストの 3 件だけです。
- 99.95% から 100% に上がった中身は、性質の違う 2 つの修正です。
  - 7 件は検索側の修正(旧字の対応表を追加)
  - 55 件は判定側を緩めた修正(CSV_EXTRA_PREFIX を新設)
  - 根拠はコミット 1af84fa です。

### 4.3 弱点【事実】

- 郵便番号は行を一意に決めません。120,677 種類の郵便番号に 124,822 行が対応し、1,548 の郵便番号は複数行を持ちます。このため、同じ郵便番号に既存の失敗があると、新しい失敗が「継続」に紛れます。
- 合格のまま分類が変わる変化(EXACT → HOUMU_PREFIX など)は見えません。
- `--update-baseline` を付けると、終了コード 1 を返す前にベースラインを書き換えてしまいます。退行を検出したのと同じ実行で、その退行を受け入れてしまいます。
- ベースラインが無いときは終了コード 0 になります。プログラムが落ちたときも終了コード 1 なので、退行と区別できません。CI の設定もありません。
- NDJSON のスナップショットは gitignore されていて、meta にハッシュがありません。日本郵便の URL は最新版しか配らないので、同じ入力で再現できません。
- 報告ファイルの名前がスナップショットの日付なので、同じ入力で再実行すると以前の報告が上書きされます。

### 4.4 gomisute-gps への移植案【推奨】

| 層 | 正解の出典 | テストケースのキー | 分類 |
|---|---|---|---|
| L1 現行名 | KEN_ALL の第 1 列(5 桁の団体コード)。address2houmukyoku は捨てている | 行のハッシュ | OK / COARSER(区が欠ける)/ ORACLE_NOISE(郡・島名の差)/ MULTI / WRONG / NONE |
| L1 旧名 | muni_alias の各行に「旧名+町名」を付けた入力 | alias 行の ID | ALIAS_OK / ALIAS_MULTI / ALIAS_WRONG / ALIAS_NONE |
| L2 町字 | ABR mt_town(各行が自分の machiaza_id に戻るか)と KEN_ALL の町域(継続行を結合してから使う) | (lg_code, machiaza_id) | EXACT / KEY_FOLD_MULTI / WRONG / NONE |
| L2 旧町名 | 国勢調査の差分(金沢 10 件)と文献調査(19 町: 確認 13 / 訂正 5 / 根拠不足 1) | alias_id | 後継の集合が一致するか |
| zone | 地理院の住居表示点。ランダムな点ではなく街区単位またはタイル単位でホールドアウトする。ABR の地番代表点(金沢 28.7 万筆)も使う | 地理院の uri、または (lg_code, machiaza_id, blk, rsdt) | OK / AMBIG_WITH_TRUTH(候補に正解を含む)/ CONFIDENT_WRONG / NO_ZONE |

あわせて、次のことを決めておきます。

- **ベースライン**: 全ケースの予測値(lg_code・machiaza_id・zone_id)を保存します。失敗だけでなく、合格どうしの答えの変化も退行として数えます。自治体ごとの集計にも閾値を置きます(ホールドアウト精度が X ポイント下がったら失敗、件数が変わったら失敗、など)。
- **2 つのコマンドに分ける**: 判定だけをする読み取り専用の `verify diff` と、`verify accept --reason …` に分けます。accept には fix_kind(system / oracle / data)と理由を記録します。報告の先頭には oracle_version と rule_set_version を書きます。
- **終了コード**: 0 / 1 / 2 は address2houmukyoku と同じ意味にし、3(取得の失敗や実行基盤の異常)を足します。
- **スナップショットの meta**: {source_url, fetched_at, 生アーカイブの sha256, 正規化後の sha256, 行数, parser_version} をコミットします。生データは R2 など git の外に日付ごとに置きます。報告の名前は「実行日 + スナップショット日」にします。
- **KEN_ALL の読み方**: 本物の CSV パーサで読みます。複数行に分かれた町域を 1 つにまとめます。記録を数えた結果では、括弧が行をまたぐ断片が 208 行あります。フラグ列(第 9〜14 列)は残します。1 行 1 レコードの UTF-8 版があれば、それを使うと楽です(要確認)。
- **gomisute-gps 側の現状の注意点【事実】**
  - `split_blocks.py --holdout` は、80% の点で作った区域で本番の `out/kanazawa_zones.geojson` などを上書きしていました。2026-10-17 に修正済みです。今はホールドアウトのときは本番の成果物を書かず、結果を `out/kanazawa_holdout.json` に出します(精度 96.08%、n=9,309)。
  - ホールドアウトの正解は、同じ規則表から作っています。区域表そのものの誤りは、この検証では見えません。
- **精度の公表**: 層ごとに、使った正解の出典を明記して公表します。1 つの数字で「今日のごみが正しい」とは言いません。

## 5. 取得・LLM 抽出パイプラインの知見

### 5.1 address2houmukyoku の仕組み【事実】(`scripts/fetch-houmukyoku.ts`)

**取得**

- 索引ページから、管轄表のページを 50 件集めます。40 件未満なら中止します。
- 各ページから管轄表(table.jurisdictiontable)と見出しだけを切り出し、それだけを LLM に渡します。

**LLM の呼び出し**

- `claude -p` をヘッドレスで子プロセスとして起動します。
- モデルは sonnet、出力は JSON です。JSON Schema で形を強制します(列挙型、最小長、追加プロパティ禁止)。
- ツールは渡さず、セッションも保存しません。プロンプトは標準入力から渡します。
- 結果の structured_output を取り出したあと、zod で二重に検証します。

**並列と失敗時の扱い**

- 同時に 6 件まで実行します。1 回の時間制限は 300 秒です(別名の抽出では 600 秒)。
- 1 ページでも失敗すると、その回は出力を書きません。ただし成功したページはキャッシュに残るので、次の実行は失敗したページだけをやり直します。キャッシュがチェックポイントの役割を果たしています。

**キャッシュ**

- キーはページの slug です。管轄表の HTML の sha256(先頭 16 桁)が変わらない限り有効です。
- キャッシュのディレクトリは SCHEMA_VERSION(v2)ごとに分かれているので、スキーマを変えると全件が無効になります。
- **取得した生の HTML は保存しません。**

**全体の妥当性確認**

- 47 都道府県があること、行数が 1,500〜2,200 であることを確かめます。外れても警告するだけです。
- 前回との差分も出しますが、条件の列を見ていないので、条件だけの変化は差分に現れません。

**プロンプトの規則**(要約)

- 郡でまとめた記載は町村ごとに展開する
- ふりがなや注記を除く
- 条件は市区町村名と別に持ち、元の記述を必ず添える
- 50 音の見出し(あ行 など)を捨てる
- 「のうち」のブロックや「の一部」ごとに行を分ける
- 「郡の内」は見出しであって条件ではない
- 郡しか書かれていないときは、構成町村をモデルの知識で補う。これは誤りを作りやすい指示です。

**手作業の修正**: `scripts/patch-okayama.ts` は、岡山のキャッシュを手書きの 33 行で置き換えます(条件付きは 8 行)。LLM が「の一部」「のうち<字の一覧>」を平らにしてしまったためです。handPatched という印を付けますが、取得側はこの印を見ません。表のハッシュが変わると、手作業の修正が黙って上書きされます。

**ドリフト検査**: 検査が読むのは、旧スクレイパーが保存した `scraphtml/*/20250130.html`(50 件)です。取り直した HTML ではありません。そのため、手順どおりに回すと 2025 年 1 月の HTML と比べることになります。

### 5.2 月次差分監視への応用【推奨】

HANDOFF.md の「次にやること 5」(ハッシュ差分抽出の流用)を具体化します。

1. **取得は 1 本にまとめる**: 取得器は 1 つだけにし、(lg_code, url, 取得日) ごとに生の HTML/PDF を R2 に保存します。manifest は {url, fetched_at, etag, last-modified, 生データの sha256, 本文の断片を正規化した sha256} とし、git にコミットします。ドリフト検査と抽出は同じバイト列を読みます。
2. **抽出キャッシュ**: キーは (断片のハッシュ, schema_version, prompt_version, model) です。スキーマは zone 規則用に {zone_name, members[{town, chome, banchi_range?}], condition{type, areas[], detailsUrl?, rawText(必須)}} とし、Python では pydantic で二重に検証します。検証に失敗したら、実行全体ではなくそのページだけを失敗にします。
3. **上書き表**: 手作業の修正は overrides/ にデータとして置き、キーを (lg_code, source_url, expected_hash) にします。ハッシュが合わなければ「古くなった」と印を付けて終了コード 2 を返し、再抽出で上書きはしません。別名の補正も同じく、生出力に手を付けない別工程にし、理由を分類して(renamed_missed / later_absorption / intermediate_target / wrong_county / hallucinated)evidence に残します。
4. **マーカーの網羅検査**: 元資料に出てくるマーカーを、別個のセルごとに数えます(一部・除く・以外・のうち・の内・番地・号棟・以北/以南/側・集積所・全域・旧)。この数と、raw_text を持つ例外の行数を比べ、元資料のほうが多ければ再抽出するか手作業で直します。address2houmukyoku の分類器は自治体ごとに数えて件数を膨らませ、八丈支庁の除外も取りこぼしていました。この 2 点は真似しないでください。
5. **状態を 3 つ持つ**: 未変更 / 変更したが構造は不変(受け入れ済み)/ 変更あり・未承認(終了コード 2)。ごみの資料は 4 月・12 月・9 月の切り替えで頻繁に変わるので、未承認のまま終了コード 2 を返し続けないようにします。
6. **規模**: 50 ページから、約 1,741 自治体 × 複数の資料に増えます。同時実行数とアクセス間隔は、自治体サイトに負荷をかけない値にします。「郡のメンバーを知識で補う」のような指示は禁止するか、inferred=true の印を付けて、ABR の match_key で照合できた場合だけ受け入れます。
7. **旧地名の手がかりを集める**: 管轄表やごみ資料に出てくる「旧X町を含む」「旧X町（現Y市）」(法務局ページでは山口・長野で 8 件)を正規表現で拾います。source=municipal_doc の別名候補として登録します。

## 6. 特殊分割(のうち/を除く/の一部)とごみ区域の例外の対応表

**【事実】** 法務局データに出てくる特殊分割は次のとおりです。

- `data/houmukyoku.json` の条件付きの行は 30 行です(include 18 / exclude 7 / partial 5)。対象は 12 の市区町村と、東京都「八丈支庁の管轄区域」の 1 行です。
- `scripts/scan-special-splits.ts` は 55 件を検出しました(の内 34・旧… 8・管轄に属する地域 4・のうち 4・を除く 3・の一部 2)。
- `scripts/analyze-special-splits.ts` の分類は other 23 / list 16 / include 8 / exclude 5 / partial 2 / complement 1 です。

**【事実】** 検索側(`src/search.ts`)での条件の評価は次のとおりです。

- 次のどれかに当たると「曖昧」として扱い、候補を両方返します。
  - partial である
  - 区域がすべて抽象的(支局・出張所・管轄 を含む)
  - 市名のあとの入力が 2 文字未満
- それ以外の include と exclude は、部分文字列が含まれるかどうかで判定します。

**【事実】(計測)** この評価方法による誤りを確認しました。

- 灘区 が 東灘区 に、東区 が 名東区 に含まれるため、両方に当たってしまう
- 「旧豊栄市地域」を抽象的な区域と判定できない
- 1 文字の字(成田市の 所・高)が入力のどこにあっても当たる。住所の末尾に「成田市役所」を付けると答えが変わる
- 別名置換で「（金山町を除く）」という文字列が入力に入り込み、include 判定に当たる。その結果、旧 下呂町・萩原町 の住所が別の支局に振られる

| 法務局側の区分 | 表記の型 | address2houmukyoku の扱い | gomisute-gps での対応【推奨】 |
|---|---|---|---|
| include | 「X のうち A、B…」 | 部分文字列が含まれれば当たり | zone.members に明示的に列挙する。丁目の範囲(1〜4丁目、1・2丁目)はコードで展開する。照合は町字の先頭からの一致で行う |
| exclude | 「X(A を除く)」 | 判定を反転 | members を「自治体の全町字 − 一覧」にする |
| 参照による除外 | 「〇〇支局の管轄に属する地域を除く」 | 曖昧 | `complement_of: zone_id` を持たせ、2 回目のパスで解決する(ごみ資料の「〇〇地区以外」にあたる) |
| partial | 「X の一部」+ 詳細ページ | 曖昧(区域の一覧が無い) | `exceptions[type=unresolved_partial]` とし、確信度を低くして候補を返す。detailsUrl は取得待ちの列に入れる |
| complement | 「…を除く県全域」 | 法人登記の補集合 | 優先度が最も低い、残り全部を受ける区域(「上記以外」) |
| list | 「〇〇郡の内」 | 見出しなので条件ではない | 例外にしない |
| 旧地名の注記 | 「旧X町を含む」「旧X町(現Y市)」 | other | muni_alias / town_alias の候補にする(§5.2 の 7) |
| 抽象ラベル | 「旧豊栄市地域」、区画整理の仮称 | 検出できずバグになる | 型付きの実体として持つ。旧市町村を指すなら L1 の別名で解決し、町字でなければ town_alias の relation=provisional / remnant にする。文字列が含まれるかで判定しない |
| (該当なし。法務局データは字まで) | 番地範囲・道路の片側・団地や集積所 | — | banchi_range / road_side / building |

共通の原則は次の 3 つです。

- すべての例外に raw_text(元の記述)を残す
- 別名の行き先には ID だけを書き、条件の文字列を入れない。条件は zone 側に持つ
- 1 文字の字を許すのは、先頭からの一致で照合するときだけにする

## 7. やらないこと / 注意点

- **コードを写さない**: address2houmukyoku は非公開です。この文書は、考え方・データの形・数値・ファイル名を記述しているだけです。実装は gomisute-gps で独自に書きます。旧字 18 組の一覧は文字の対応という事実であり、コードではありません。
- **別名ファイルをそのまま取り込まない**(§2.5)。address2houmukyoku で畳み込んだ文字列は保存しません。2 つのシステムの間で、生の文字列どうしを比べません。
- **「124,822 件・100%」を根拠として引用しない**: この数字は市区町村名が両立するかを見ただけです。別名、支局の正しさ、答えが 1 つに決まるかは検証していません。gomisute-gps の L1 の精度の根拠にもなりません。
- **LLM 抽出データの信頼度**: 出典のない LLM 由来のデータで、検証をすり抜けた誤りが少なくとも 1 件(新冠町)あります。confidence は 0.8 で始め、ABR と照合して検査を通った行だけ 1.0 にします。派生データを公開リポジトリに置くかどうかは、所有者が判断してください。
- **鮮度**
  - aliases は 2026-05-05 時点のもので、2026-05-08 の houmukyoku.json v2 に合わせて作り直していません。v2 に無い後継が 27 件あります。
  - 期間は 2019-05-01 までで、浜松市の 2024 年の区再編は入っていません。
  - ドリフト報告は条件行を 28 と数えていますが、現在のファイルには 30 行あります。
  - 取り込むときは、元ファイルの lastUpdated を source に残します。
- **真似しない構成**
  - 部分文字列スコアリングと全件の線形走査。L1 は約 1.9k 行なので十分速く、1 件あたり約 74 µs です(計測)。L2 の 727k 行には D1 の索引が必要です。
  - Workers Sites の `[site]` バケットを data ディレクトリに向けること
  - 開発用とデプロイ用で HTTP の入口が 2 つに分かれ、中身がずれていること
  - 手作業の修正の印を誰も見ないこと
  - 弾いた行を保存しないこと
- **数え方**: mt_city の区以外の行 1,747 は、1,741 + 北方領土 6 村です。「1,747 = 1,741」という前提は置かないでください。
