# LLM の読み取りの比べ: DeepSeek と Opus (2026-10-21)

同じ資料・同じ問いかけ (llmread.p1) を DeepSeek (deepseek-flash) と Opus 5.5 (claude-opus-5-5) に渡し、
返った JSON から Python が日付を計算して、正解と比べました。
作者 firemio の決め方は「どちらも正しければ DeepSeek を使う (安い)」です。

- 資料: 計画 `out/llmread/plan.json` のキャッシュにある 87 本をすべて読みました。止めたものはありません
  - tier A の 16 自治体の 70 本 (秩父市はキャッシュに資料が無く、計画の外です)
  - 女川町の 12 か月 (12 本)
  - 金沢市の 5 地区 (5 本)
- 費用の上限 (Opus $60・DeepSeek $5) には届きませんでした。実際は Opus $27.15、DeepSeek $2.34 です
- 正解
  - tier A: japan-gomi-data (tecolicom、CC BY 4.0)
  - 女川: `out/onagawa_reading.json` の final
  - 金沢: `out/kanazawa_schedules.json`
- 結果の数字: `out/llmread/results.json`
- モデルの生の答えと使ったトークン: `out/llmread/raw/<モデル>/`

## 結論

**DeepSeek は Opus ほど正しくありません。**

- 日付がすべて合った系列は、DeepSeek が 761、Opus が 1,198 です (どちらも 1,652 系列中)
- 年末年始のほかにも違う日を出した系列は、DeepSeek が 177、Opus が 3 です
- 「答える」とした系列で違う日があったものは、DeepSeek が 77、Opus が 0 です

資料の種類で分けて決め方に当てはめると、次のとおりです。

- **文字の PDF・画像の PDF: Opus を使います。** DeepSeek は読み違いが多く (日付ごと別の曜日や別の隔週の組にする、結合したマスを取り違える)、そのまま「答える」側にも出ます。答えが返らない資料もありました (87 本中 3 本。1 回聞き直しても同じでした)
- **HTML の表・CSV: 日付がすべて合った系列の数はほぼ同じです** (HTML の表は 143 対 142、CSV は 99 対 99)。それでも「どちらも正しい」とは言えません
  - DeepSeek にだけ、年末年始以外の読み違いが 9 系列ありました。「火曜日 第2・4 空きびん・缶」を毎週の火曜日と読む、CSV の表に「土曜日」とある品目を水曜日とする、などです
  - 今回は、その資料に祝日や年末年始の書きが無かったため、9 系列とも「答えない」側に入り、表には出ませんでした。書きのある資料なら、そのまま答えになります
- 費用は DeepSeek が Opus の約 1/12 です (1 自治体あたりの平均 $0.12 対 $1.51)

### 言葉の意味

- **系列**: 正解と比べる単位です
  - tier A: 正解のコース × 品目 (2026 年度)
  - 女川: 月 × 表のマス
  - 金沢: 地区 × 品目
  - そのコースの出典がキャッシュに無い 236 系列は、どちらのモデルにも資料を渡していないので数えていません
- **正しい**: 比べる期間の日付が 1 日も違わない系列
- **違う日あり**: 正解に無い日を 1 日でも出した系列
- **足りない**: 違う日は無いが、足りない日がある系列。地区や品目の名前が正解と合わずに当たらないものも、ここに入ります
- **答えを控えた**: 計算 (`calc.py`) が「答えてよい」にしなかった系列です。次のどれかに当たると控えます
  - モデルが unsure に書いた
  - 資料に祝日の扱いが無い
  - 期間が 12/31 を含むのに年末年始の扱いが無い
  - 答えが返らない
  - 正しい・違う日あり・足りないとは別に数えています
- **年末年始だけ違う**: 資料に年末年始の書きが無い系列で起きます
  - どちらのモデルも「書いていない」と unsure に書きました
  - 計算は毎週の規則を年末年始にも広げるので、正解 (別の資料から休みを持つ) と違う日が出ます
  - 読み違いではありません。控えた側に入るので、答えにも出ません
- 費用
  - DeepSeek は、全部を混む時間 (UTC 10:46〜11:32) に回した料金です
  - Opus は claude -p の total_cost_usd (API の料金で数えた値) です
  - 答えが返らずに聞き直した分の費用も含めています
- 時間は呼び出しごとの秒です。実際は Opus を 4 本、DeepSeek を 6 本ずつ並べて動かし、どちらも 17〜18 分で全部が終わりました

## 2 つのモデルの読みが同じか

| | 系列 |
|---|---|
| 両方を採点した系列 | 1,652 |

## 誤りの例

### DeepSeek

1. **女川町・毎月の「燃やせないごみ」(結合したマス)**
   - 資源の表で、粗大ごみの日を燃やせないごみの日として読み、本当の燃やせないごみの日を落としました
   - 例: 2026 年 7 月の大沢・浦宿全区・針浜
     - DeepSeek: 1 日
     - 正解: 14 日・28 日
   - 6 行 × 12 か月のほぼすべてで同じ誤りが起き、67 系列が「答える」のまま違う日になりました
2. **皆野町 コース 03 (日野沢・金沢・国神・大渕・野巻) の「紙・布類」**
   - 暦の印字は 4/8・4/23・5/12・5/27…です
   - DeepSeek は 4/7・4/21・5/5・5/19… と、隔週の火曜日の並びに作り替えました
   - 24 日すべて違い、unsure も無く「答える」側でした
3. **小鹿野町 小鹿野・伊豆沢の「燃やすごみ」**
   - 正しくは火曜日です (4/7・4/14・4/21…)
   - DeepSeek は月曜日 (4/6・4/13・4/20…) と読み、52 日すべて違いました
   - 秩父広域のマスの色の暦では、ほかの品目も同じように曜日や組がずれました
   - この系列は控えた側に入りました
4. **武蔵野市 B地区の「びん」(缶・危険有害も同じ)**
   - 印字の日付を写すとき、1〜3 月の 6 日が 1 週ずれました
     - DeepSeek: 1/8・1/22・2/5…
     - 正解: 1/15・1/29・2/12…
   - 年明けに隔週の組が入れ替わるのを見落とした形です。「答える」側でした
5. **三鷹市 新川6丁目・下連雀5〜9丁目の「空きびん・缶」(HTML の表)**
   - 「火曜日 第2・4 空きびん・缶」を、毎週の火曜日と読みました。28 日多く出ています
   - 同じ三鷹の別地区 (095687) も同じでした
   - 祝日の書きが無いので控えた側に入りましたが、書きがあれば答えになっていました

- **答えが返らない**: 日高市 (20 コースの 4 ページ)、長瀞町の 1 本、小鹿野町の 1 本です。max_tokens 32,000 を推論で使い切り、本文の JSON が出ませんでした。1 回聞き直しても同じでした
- **形の誤り**: 青梅の 1 本では、1 回目に JSON の頭へ余計な `"type": "json_object"` を付け、形の確かめで落ちました。2 回目は通りました

### Opus

Opus の誤りはどれも「足りない」側か、資料に書きの無い年末年始・1 月のものでした。Opus が「答える」とした 402 系列はすべて正しく、正しくない系列はすべて控えた側でした。下の 5 つは、どれも Opus 自身が unsure に書いています。

1. **女川町 2027 年 3 月の「燃やせないごみ」**
   - 「列はあるが、どの行政区にも日付が印字されていないように見える」と unsure に書き、日付を入れませんでした
   - 正解には 6 行で計 14 日あります。12 か月のうち、この月だけです
2. **武蔵野市 C地区の「古紙・古着」**
   - 暦で「古紙・古着缶」と 1 つのマスに書かれた日を缶だけと読み、古紙・古着を隔週としました。25 日足りません
   - 一覧表の「毎週」と食い違うことを unsure に書いています
3. **板橋区 東7 の「可燃ごみ」**
   - 資料に「年末年始の収集日は、改めて…お知らせ」とあります。Opus はこれを理由に 12/28・12/30・1/4・1/6・1/8 を入れず、unsure に書きました
   - 正解はこれらを通常の収集日として持ちます。誤りというより控えめに読んだものです (板橋の 4 系列)
4. **東秩父村の資源回収 (古紙)**
   - 第2水曜日 (役場前駐車場) を「持ち込みと読めて、ステーション収集か分からない」として入れず、第4水曜日だけを書きました。12 日足りません
   - 正解は両方を収集日として持ちます
5. **三鷹市 (095671) の「缶・びん・ペットボトル」**
   - ページに「年末及び1月は収集日程、時間が異なることがあります」とあります
   - それでも毎週・第N曜日の規則は 1 月にも広がるので、1/1・1/15 などが違う日になりました (DeepSeek も同じ)
   - Opus は unsure を書き、控えた側でした。読み違いの 3 系列はこれです

- 年末年始だけ違う 141 系列は、資料に年末年始の書きが無いためです。Opus も「書いていない」と unsure に書きました (読み違いではありません)
- 日高市のコース 9 は、Opus が印字のまま「東急こまがわ１・２・３・４」と 1 つで書きました。正解は「東急こまがわ1」… と分けて持つので名前が合わず、当たりませんでした (採点の当て方の限り)

## 採点の限り・注意

- 地区と品目の当て方は名前が合うものだけです
  - 290 系列 (世田谷 204・中央区 72・日高のコース 9 など) は、どちらのモデルも当たりませんでした
  - これはモデルの読みの良し悪しではありません
- tier A で「控えた」の大半は、資料側の理由 (祝日・年末年始の書きが無い) です
  - モデルが自分の迷いに気づいて止めたわけではありません
  - DeepSeek にだけある HTML・CSV の読み違い (三鷹 6・杉並 3 の 9 系列) は、今回たまたま控えた側に入りました
- tier A は、モデルが書いた期間と正解の期間の重なりだけで比べます (`score.py` の作り)

## 道すじ

- 動かし方 (鍵は DeepSeek だけに渡します)
  - `GOMISUTE_LLM_API_KEY=... python nationwide/llmread/full.py ask`: 上限つきで計画のすべてを聞きます。答えがあれば聞き直しません。失敗したものは 1 回だけ聞き直し、失敗の記録は `<doc_id>.try1.json` として残します
  - `python nationwide/llmread/full.py report`: `out/llmread/raw/`・`inputs.json`・`scores/`・`results.json` を作ります
- 採点の作り直し (モデルを呼びません): `python -m nationwide.llmread score --check`
  - `out/llmread/raw/` の生の答え、`out/llmread/inputs.json` (資料ごとの種類・ページ数・文字数)、計画と正解だけから、この文書の数字のもとの `results.json` と `scores/` を作り直し、今のものと 1 つも違わないか確かめます
  - japan-gomi-data の正解は先に `python nationwide/llmread/jgd.py fetch` と `convert` で用意します
  - `--check` を付けないと、`scores/` と `results.json` を書き直します
- `out/llmread/results.json`: 資料ごと (費用・トークン・秒・形の確かめ) と系列ごと (モデルごとの correct/wrong/missing と abstained・違う日の見本) の結果、種類ごと・対象ごとのまとめ、2 つのモデルの読みの一致
- `out/llmread/raw/deepseek-flash/`・`out/llmread/raw/claude-opus-5-5/`: 生の答えと使ったトークン
  - DeepSeek は API の content と reasoning_content です
  - Opus は claude -p の result です
  - 家のフォルダの道すじは伏せています。鍵は書かれていません
- `out/llmread/scores/`: 対象ごとの採点の細かいもの
- `out/llmread/inputs.json`: 資料ごとの入力の記録 (種類・ページ数・文字数・入力の sha256)
- `out/llmread/run_log.json`: 実行ごとの費用・聞き直し・止めたもの (止めたものは 0)

## 別の担当の確かめで分かったこと (2026-10-21)

モデルは呼ばずに、保存した生の答えから採点を作り直し (別に書いた採点でも作り直し)、数字が results.json と 1 つも違わないことを確かめた。
2 つのモデルは 87 本すべてで同じ入力・同じ問いかけだった (違うのは画像の渡し方だけ)。そのうえで、読むときに気をつけること:

- **中央区の「DeepSeek だけ正しい 8 系列」は採点の当て方の都合**: DeepSeek が地区を「豊海町」「全域」と分けて書き、それが正解の名前に当たっただけ。
  空白・「全域」をそろえて当てると、両モデルとも 72 系列すべて正しく読みも同じ。HTML の表の「143 対 142」と「DeepSeek だけ正しい 14」は、この分だけ DeepSeek に有利
- **女川の正解は Opus のエージェント 2 人の読みで作ったもの** (人の目では確かめていない)。Opus に有利な循環の恐れがある。
  ただし、DeepSeek に表の構造を渡したパイロット (計画書 §6) は同じ正解と 323/324・324/324 で合い、今回の DeepSeek の誤り (粗大ごみの日を燃やせないごみの日と読む) も展開して確かめた
- **Opus の費用は CLI を通した分だけ高い**: Claude Code の system プロンプトは置き換えている (1 回あたり約 1,000 トークン、全体で約 $0.10)。
  高くなった主な理由は、(1) 入力を 1 時間のキャッシュに入力の 2 倍の値段で書いている (約 +$7.9)、(2) PDF のページを 1 枚ずつ Read のターンで読んでいる。
  API に画像を直接添えて 1 回で聞けば、Opus の費用は下がる見込み (一括の Batch API ならさらに半額)
- DeepSeek は 1 回の試行の中で、JSON として読めない答えを最大 4 回まで聞き直している (Opus には無い)。DeepSeek に有利な側
- 日高の DeepSeek は、多くが本文の JSON を出している途中で出力の上限で切れた (推論だけで使い切ったのは長瀞・小鹿野の 2 本)
- 試行は 1 回だけ。同じ資料での読みの揺れはまだ測っていない
