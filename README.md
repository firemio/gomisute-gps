# gomisute-gps — LLM が「今日出せるごみ」を確かに答えるための、唯一の情報源

*Built with Claude Code — [Built with Claude: Japan 2026](https://cerebralvalley.ai/e/built-with-claude-japan2026) 応募作品 / 作者: [firemio](https://github.com/firemio)*

## そもそもの問題: 自治体ごとに別々の IT 契約で、まとまりがない

ごみ出しのルールは、**各自治体がそれぞれ別の事業者と、ごみ分別アプリ・収集カレンダー・Web ページなどを個別に契約して**配っています。
そのため、

- 配り方も形式もバラバラ (PDF、HTML の表、アプリの中だけ、CSV や zip のオープンデータ…)。
  12 自治体を調べた範囲で、機械可読なオープンデータを出していたのは長野市 (zip) と世田谷区 (CSV) だけでした
- 全国をまとめたデータも、共通の形式もない
- 結果として、**LLM が参照できる「確かな情報源」が存在しない**。AI アシスタントに「今日このごみ出していい？」と聞いても、
  古い情報や推測で答えるしかありません

## 目的: LLM が唯一確かな情報源として使えるデータと API を作る

行政が形式を統一しないなら、民間側で全国 1,741 自治体分を集めて構造化し、1つの形にそろえる。
gomisute-gps は、**LLM がそのまま根拠として使える**ごみ収集データの基盤を目指す研究実装です。

- 緯度経度ひとつで「収集地区 → 今日・明日出せるごみ」を返す
- すべての答えに**出典** (自治体の資料の URL・取得日時・ハッシュ) と**確信度**を付ける。LLM は根拠を示して答えられ、確信度が低いときは候補を返して利用者に確かめさせる
- 自治体の資料の更新を差分で追い続け、古い情報を返さない

## なぜ難しいのか (データの中身もバラバラ)

ごみ収集日は「住所 → 収集地区 → 曜日ルール」の2段引きですが、どちらの段も自治体ごとにバラバラです。

| 問題 | 実例 |
|---|---|
| 収集区域ポリゴンを公開している自治体は **0** (12自治体を調べた結果) | 区域は町丁目名のリストで配られる |
| 町丁目より細かい区切りがある | 番地範囲 (横浜・大阪・金沢・札幌) / 道路境界 (宇都宮) / 団地・集積所単位 (世田谷・大阪・高知) |
| 区域表に**もう存在しない町名**が残っている | 金沢: 住居表示で消えた「笠舞町」「西念町」などが現役で載っている |
| 日付ルールが「第N曜日」とは限らない | 長野: 月1回品目は**28日ローテーション**で、GW・年末に位相がずれる |
| 更新周期がバラバラ | 年度(4月)・暦年(12月)・秋(9月)・2か月ごと |

## ここまでの成果

### 1. 収集日ルールの正規化 (`normalize.py`)
- **世田谷区** (CSV オープンデータ): 118行 / 275町丁目 / 472スケジュール → RRULE。パースエラー0、LLM不要
- **長野市** (365日×品目の○マトリクス zip): 366スケジュールを
  単一RRULE 112 / 区間分割RRULE 250 / 明示日付 4 に圧縮し、**全件を元データと往復一致**で検証

### 2. 収集区域のポリゴン化 (`kz_tables.py` → `kz_rules.py` → `split_blocks.py`)
金沢市の区域表 HTML (1,776ルール) × e-Stat 町丁目ポリゴン × 地理院 住居表示点 (12万点) から、71収集地区のポリゴンを生成。

- 914町のうち町丁目まるごと 793 (86.8%)、残りは住居表示点のボロノイ分割
- 面積カバー率 96.6% / 重なり 0 / 全市 4 秒
- **20% ホールドアウト精度 96.2%** (分割町のみ、n=9,232、`out/kanazawa_holdout.json`)

![金沢市 収集地区](out/kanazawa_map.png)

### 3. 旧町名の検証 — ABR は「履歴台帳」ではなかった (`fetch_abr.py` → `abr_check.py` → `census_lineage.py`)
ポリゴンが引けなかった32町を、デジタル庁 アドレス・ベース・レジストリ (ABR) で検証しました。

- ABR 町字マスター (全国 727,467 行) には**廃止日・別名が1件も入っていない**。効力発生日の 98.6% は 1947-04-17 (地方自治法施行日のプレースホルダ)
- しかも **ABR に無い ≠ 廃止**。郵便番号が現役の北安江町・西念町や、地番の登記が無い残存地 (西堀川町・笠舞町など) も ABR から漏れている
- 32町の内訳: ABR にも国勢調査2020にも無い 15 / 旧町名＋イロハ小字の行だけが残る 3 / 区画整理の仮称 1 / 区域表が丁目を省略 3 / ABR に現存するが国勢調査2020に無い 10
- **国勢調査小地域 2000→2020 の差分**を面積按分すると、消えた町名と後継町を機械的に取り出せる (金沢で10件)。それより前は、Claude の調査エージェントが市の換地図 PDF・県公報の告示番号・郵便番号簿を当たり、別の反証エージェントが検証した (19町: 確認13 / 訂正5 / 根拠不足1)
- 町名は数十年かけて段階的に消え (柳町 1965→1992→1993)、別の範囲で復活もする (観音町 2019)。→ 正規化 Worker は「町名→町名」の表ではなく**変更イベントの履歴**として設計した ([docs/address-normalize-schema.md](docs/address-normalize-schema.md))
- ABR 地番マスター位置参照拡張 (金沢 28.7万筆の代表点) は、字・地番型の区域分割に使える → `resolve.py` v5 で、住居表示の無い地域の索引として使った

詳細は [docs/abr_check.md](docs/abr_check.md)、系譜データは `out/kanazawa_town_alias*.csv`。

### 4. 金沢で「緯度経度 → 今日のごみ」まで通した (`kz_calendar.py` → `resolve.py`)
緯度経度と日付から「収集地区 → その日に出せるごみ」を、出典と確信度を付けて返す参照実装です。

```
$ python resolve.py 36.481532 136.703003 2026-10-20
この場所 (樫見町の町域) は金沢市の犀川地区 (収集カレンダー上の地区名) です。10月20日(火)は燃やすごみ。10月21日(水)はびん。
出すのは収集日の午前8時30分まで (金沢市「ごみの出し方のルール」)。
出典: 金沢市「2026年度地区・校下別収集カレンダー(その3) — 犀川（西部管理センター）2026年度版」。地区の確信度 0.95。
```
(実際の出力は JSON。上は `summary_ja` の値)

- **収集日**: 市の「2026年度 地区・校下別収集カレンダー」(HTML の表) から、71地区 × 5品目 = 355件
  - 燃やすごみは曜日の規則 (火・金 または 月・木) と年末年始の休み、ほかの品目は月ごとの実日付。実日付を正とし、RRULE への圧縮は全件が元の日付に戻ることを確認
  - 規則 (第N曜日) と表の日付が違うのは2026年12月・2027年1月だけ。その日は「通常の『第4金曜日』とは違う日」と明示する
  - **独立した検証エージェントが市のページを自分で読んで作った正解と、71地区 × 365日 = 25,915回すべて一致** (v4 の最終検証でも、`resolve.py` の出力 26,838 地区・日で一致)
- **地区の判定** (`resolve.py` v5): 公式の根拠 (区域表の行) から出てくる地区が **1つだけ**で、その地区が**この場所を直接指す根拠**
  (最寄りの住所・地番の行、区域、町の行) を持つときに限り確定する。そうでなければ候補を全部返す
  - 候補にする根拠:
    - 最寄りの住居表示住所 (国土地理院) を区域表の行に直接当てる / 25m 以内の別の住所 (行が決まらない住所は、その町の地区を全部)
    - **最寄りの地番** (デジタル庁 ABR 地番代表点、住居表示の無い筆 24万) を区域表の行に当てる / 80m 以内の別の地番。
      区域表の地番の行 (「ロ21」「南638から794」「中平ムを除く」) は確実に読める形だけを使い、条件付きの行 (「リ≪犀川右岸≫」「犀川右岸」) や
      読めない行 (「12の」)、今の地番に無い番地範囲の行 (福増町「南638から794」) がある所では無理に決めない (`kzrules.match_parcel`)
    - **地区が分かれる町では、地番だけで確定しない**。住居表示の無い筆の 55% は ABR に位置が無く、最寄りの位置つきの地番が利用者の地番とは限らないため。
      近くに地区が分かれる町の地番があるときも、その町の地区を全部候補にする
    - 区域表から作った区域ポリゴン / 10m 以内の別の地区の区域
    - **住居表示住所が1つも無い街区** (位置は ABR の住居表示 街区代表点。町を問わず 120m 以内)
    - 区域が無い場所では国勢調査の町の行
  - 次の場合は確定しない (`unresolved`)。理由は `decision_blocked_by.reason` に入れ、区域表の行による候補は `official: true` のまま返す
    (`official: false` は旧町名の系譜からの推定 `inferred_lineage` と、よく似た町名の条件付きの行 `conditional_similar_row` だけ):
    - `place_town_not_in_rules_table`: この場所の町 (25m 以内の最寄りの住所か 30m 以内の地番。住所がまばらなら 50m 以内の最寄りの住所) が区域表に無い
    - `census_town_not_in_rules_table`: この地点を含む国勢調査の町が区域表に無い
    - `near_municipal_boundary`: 隣の市町との境界 (国土数値情報 行政区域、海岸線を除く) が 10m (+ 位置の誤差) 以内。金沢市かどうかも言い切れない
    - `nearby_town_not_in_rules_table`: 25m (+ 位置の誤差) 以内に、区域表に無い町の住所・地番・国勢調査の町がある
    - `rules_table_note`: 決め手の行に注記がある (主計町: 馬場地区に割り当てつつ「(注意)実際の地区とは異なります」)
    - `no_official_row` / `outside_town_polygons` / `accuracy_too_low` (99% の半径が 300m 超): 区域表の根拠が無い・町の区域の外・位置の精度が低すぎる
  - 位置の誤差は 10m 以内を前提にする。端末が返す精度 `accuracy_m` と、その半径に本当の位置が入る確率 `accuracy_confidence`
    (既定 0.68 = Android の `getAccuracy`。Android の Chrome もこの値をそのまま `coords.accuracy` に渡す) を渡すと、本当の位置が 99% の確率で入る半径
    (0.68 なら約2.0倍) を求め、すべての根拠の距離にその半径を足して探す
  - 唯一の「推定を含む確定」は、国勢調査の町名が区域表に無く、よく似た町名の**町全体の行**だけがある場合 (国勢調査の 新竪町 ⇔ 区域表の 新竪町3丁目)。
    `location.inference` に「区域表に 新竪町 の行は無く、よく似た町名 新竪町3丁目 の行 (町全体) から推定」と明記する。
    近くに住所・地番の行があれば (諸江町中丁 など) それが決め手になり、`inference` は付かない
  - 評価 (`python eval_resolve.py`)。正解はその住所 (地番) を区域表の行に当てた地区。区域表で決まらない住所での確定は誤りに数えた値も出す:

    | 評価 | 条件 | 確定 | 確定した答えの正しさ | 表で決まらない住所での確定も誤りに数えると |
    |---|---|---|---|---|
    | 完全ホールドアウト | 住居表示住所の 20% (24,159件、うち表で決まる 23,953件) を、住所の索引からも区域ポリゴンの作成からも外して「利用者の位置」として引く | 83.4% | **100%** (誤り 0) | 99.99% (2件) |
    | 街区ホールドアウト | 街区の 10% を住所ごと丸ごと外す (利用者の街区に住所データが無い場合)。シード 1・2 (表で決まる 24,366件) | 76.7% | **100%** (誤り 0) | 99.54% (86件) |
    | 〃 (調整に使ったシード 314 を含む3つ) | 表で決まる 35,896件 | 75.8% | **100%** (誤り 0) | 99.69% (86件) |
    | 地番ホールドアウト | 住居表示の無い筆の 10% (23,981件、うち表で決まる 23,219件) を地番の索引から外して、その代表点で引く | 81.1% | **99.98%** (誤り 3) | 99.98% |
    | 小字ホールドアウト | 町+小字の 10% を丸ごと外す (ABR の位置の欠けは小字まるごとに起きる: 欠けの 87%)。表で決まる 18,914件 | 86.0% | **99.71%** (誤り 47) | 99.71% |
    | 地区が分かれる町の地番 | その町の筆の 25% (4,473件、うち表で決まる 2,908件) を外す | 0.03% (1件) | 0% (その1件が誤り) | 表で決まらない地番では 2件で確定 |
    | GPS のずれ 10m | 本番のモデルで、住所 3,000件 × 10点を各住所から 10m 以内に打つ | 83.7% | **100%** (誤り 0) | 100% |
    | GPS のずれ (円の中) | 住所 3,000件 × 5点を 30m 以内に。`accuracy_m` を渡さない / 30m を確実な上限 (確率 0.99) として渡す / 50m で渡す | 84.1% / 60.7% / 50.0% | 99.72% (誤り 35) / **100%** / **100%** | 同左 |
    | GPS のずれ (端末の精度どおり) | 2次元正規分布の誤差 (3,000件 × 5点)。Android 式 (半径に入るのは 68%) で `accuracy_m` = 20 / 30 / 50m | 55.9% / 45.5% / 28.9% | **100%** (誤り 0) | 100% |
    | 〃 | 半径に入るのが 95% の端末で `accuracy_m` = 30 / 50m (`accuracy_confidence=0.95`) | 57.4% / 44.7% | **100%** (誤り 0) | 100% |
    | 〃 | Android 式 30m で `accuracy_m` を渡さない | 84.2% | 99.17% (誤り 104) | 99.16% |

    - 「誤り 0」はこの標本での値。99% の半径の外に本当の位置がある 1% の場合は誤りうる (検証エージェントの別の模擬では、確定 1万件に 1件ほど)
    - 確定しなかった場合も、多くは候補の中に正解がある。無いのは、10m を超える GPS のずれで `accuracy_m` を渡さない場合 (30m 以内で 1件、正規分布 30m で 7件)、
      地番の代表点が国勢調査の町の外にある場合 (地番 10件・小字 16件、市外扱い)、小字ホールドアウトのその他 25件
    - 街区ホールドアウトの 86件は、区域表に無い町の街区を丸ごと外した場合: 木ノ新保町 47件 (国勢調査と ABR の住居表示にはあるが区域表に無い。
      住所の位置が国勢調査では隣の町の中) と、金石下寺町・金石浜町・金石上浜町 39件 (**国土地理院の住居表示住所にだけある町名**。
      国勢調査・ABR の住居表示・区域表のどれにも無く、ABR では地番の町名としてだけ残る)。外すとそこが表に無い町だと知る手がかりが無く、
      隣の町と同じ地区で確定する。本番ではこれらの住所が索引にあり、近くにあれば `unresolved` になる
    - 地番の誤り 3件は山間部の境界: 平栗ツ46 (ABR の代表点が国勢調査の新保町の中にある)、福久町レ98 (月浦町の筆に囲まれている)、
      福久町弐字22 (ABR の代表点が国勢調査の北陽台3丁目の中)
    - **小字ホールドアウトの誤り 47件** (住吉町オ・福久町弐字・浅川町ハ など) は、利用者の小字ごと ABR に位置が無く、その土地が国勢調査では隣の町の区域に入っている場合。
      近くに住所も地番も無いときに区域だけで確定しないようにすると (`AREA_ALONE_OK=0`)、誤りは 28件に減るが確定率は 56% に下がるので、既定では入れていない。
      直すには登記所備付地図 (筆の形) が要る
    - 地区が分かれる町で利用者の地番に位置が無いときは、ほぼ確定しない (候補を返して地番を聞く)。確定した3件 (誤り1・表で決まらない地番2) は
      どれも、筆の代表点が国勢調査では別の町 (畝田中2丁目、三小牛町) の中にある場合
    - GPS の誤差が 10m を超えるときは `accuracy_m` を渡す必要がある (渡さないと、30m 以内のずれで 0.28%、Android 式の 30m で 0.83% 誤る)
    - 距離の定数の決め方: 地番の 80m は、報告とは別のシード (7) の地番ホールドアウトで 30m: 誤り12、50m: 2、80m: 0 から決めた。
      街区の 120m は v4 でシード 314 を使って決めたので、シード 1・2 だけの値を上に分けて出した。
      住所の区域の 10m (`NEAR_M`) は、報告している完全ホールドアウト (random_state=42) そのもので 10〜30m を比べて決めた (誤りは同数、確定率が最も高い 10m)
    - 適用範囲: 確定率と正しさは、住居表示の住所 (国土地理院) か ABR の地番代表点がある場所での値。区域表の読み方 (`match_row` / `match_parcel`) は
      正解づくりにも使っているので、表の読み違いはこの評価では見えない (検証エージェントが別に読んだ結果と比べ、`match_parcel` の方が常に慎重だった)。
      区域表の番地範囲の半分以上が今の地番に無い行 (福増町「南638から794」、福久町「ロ86」など17行) は、番号が付け替わった可能性があるので、
      同じ小字では「別記以外」とは言い切らず、表で決まらない地番として扱う
  - **独立した検証エージェントとの往復で5回作り直した**: v1 は境界ぎわの点と市外判定 (金沢港の水面) で誤り、
    v2 は「近くの住所と区域が一致すれば確定」が、区域ポリゴンまで作り直す本当のホールドアウトで 1.3〜1.6% 誤ることを指摘され、
    v3 は「住所の点の真上なら確定」が GPS のずれで誤作動すること、住居表示住所の無い区域表の行 (玉川町2番など) を見落とすことを指摘された。
    v4 は住居表示の無い地域 (ABR 地番代表点で引くと 0.40% の誤り) と、区域表に無い町の住所が近くにあるときの言い方 (「この場所は表に無い」と言い過ぎる) を指摘され、
    v5 で地番の索引と `decision_blocked_by` を入れた (地番での誤り 0.40% → 0.02%)。v5 の検証では、GPS の誤差が 20m を超えると誤ること、
    利用者の地番に位置が無いと地区が分かれる町で誤ること、行の決まらない近くの住所を無視していることを指摘され、`accuracy_m`、分かれる町では地番だけで確定しないこと、
    近くの住所の町の地区を全部候補にすることで直した。さらに `accuracy_m` を確実な上限として扱うと端末の精度 (68% の半径) の外で誤ることを指摘され、
    `accuracy_confidence` で 99% の半径まで広げた。最後の並列検証 (4人) では、市の境界をまたぐ誤差、区域表に無い国勢調査の町、主計町の注記、
    小字まるごとの位置の欠け、1月の日程の変更の書き方などを指摘され、`near_municipal_boundary`・`rules_table_note` などを加えた。
    どれも「言い過ぎ (確定させてはいけない場面での確定)」で、今の版はそれを候補返しに回している
- **LLM が誤らないための出力** (ツール定義案: [docs/mcp-tool.md](docs/mcp-tool.md))
  - `status` (ok / ambiguous / unresolved / out_of_coverage / invalid_input) と `answerable`。`days`・`next_after_date` は ok のときだけ (それ以外は `candidates[].days`)
  - 日ごとの `in_calendar_range`。カレンダーの範囲外を「収集なし」と言わない。規則と違う日は `is_exception`
  - 候補ごとの根拠 (`basis`) と `official`、確定しない理由 (`decision_blocked_by`)。候補が1つなら「候補の X 地区なら」と言い、「どの候補でも」と言わない。
    `unresolved` では正しい地区が候補に無いこともあるので、`consensus` は出さず、候補ごとに「X 地区なら」と言う
  - 確定したときは場所 (25m 以内の最寄りの住所か 30m 以内の地番と距離。無ければ町名) を要約に入れ、利用者が自分の場所か確かめられるようにする
  - `put_out_by`: 出す時刻 (収集日の午前8時30分まで、市の「ごみの出し方のルール」) / `not_covered`: 分別方法・出し方・集積所の場所はデータに無い (推測させない)
  - `contact`: 金沢市 ごみ減量推進課 076-220-2302 / `sources`: 区域表 (題名・URL)、カレンダー (題名・節・URL・取得日時・表の SHA-256)、出し方のルール (題名・URL・取得日時・ページの SHA-256)
  - `holiday_policy`: 祝日も収集。2026年12月・2027年1月は燃やすごみ以外も規則と違う日がある (例: 2027-01-29) ので、その2か月は日付だけを使う
  - 要約に並べる候補は3つまで (残りは `candidates[]`)。範囲外の日は「収集なし」という意味ではないと書く
  - 市区町村は [gps2city](https://github.com/firemio/gps2city) の `lg_code` で確かめ、未対応の市では市名を返す。
    gps2city では金沢市なのに国勢調査の町の区域の外 (海岸など) なら `unresolved` (未対応とは言わない)
  - 入力の検査: 真偽値・バイト列・NaN・無限大・桁あふれの緯度経度、時刻つきの日時・2000〜2099年の外の日付、1〜14 以外の日数、0〜1000 以外の `accuracy_m`、0.5〜0.99 以外の `accuracy_confidence` は `invalid_input`

### 5. 比較実験: ウェブ検索だけの AI でも答えられるか ([docs/llm-baseline.md](docs/llm-baseline.md))
作り込みを続ける前に、「今の AI はウェブ検索だけで正しく答えられないのか」を測った (2026-10-17)。

- 金沢の住所・緯度経度と日付の 28問 (年末年始のひっかけ、1月だけ規則とずれる日、地区が分かれる町、緯度経度だけ を含む) を、
  ウェブ検索だけの AI アシスタント (Claude Opus 5.5) に1問ずつ別々に聞いた
- **その日に出せる品目は 28 / 28 正解、地区も 28 / 28 正解**。付随情報 521件のうち誤りは 5件で、どれも「何を・いつ出すか」には関係しない
- 逆に gomisute-gps が「出す時刻は公式ページに記載なし」と誤っていた (市の「ごみの出し方のルール」に午前8時30分までとある)。直した
- **結論: 金沢のように市のサイトが HTML で整っていれば、今の AI はウェブ検索だけで正しく答えられる。** gomisute-gps に残る価値は正確さそのものより、
  手間と費用 (AI 単体は1問に約18回のウェブ取得・約8万トークン)、PDF・画像・アプリにしか情報の無い自治体、軽いモデル・検索なしの環境、機械が読める形にある
- **続き: カレンダーが PDF・画像だけの5自治体** (村上市・旭川市・宮崎市・女川町・東海村、30問。[docs/llm-baseline-hard.md](docs/llm-baseline-hard.md))。
  Opus 5.5 は PDF をページの画像として見て **30 / 30 正解** (色だけの印・スキャン画像・32ページの町の暦の中の表も読んだ)。
  軽い Haiku 5.5 は **14 / 30** (誤り 1・答えられず 13)。誤りの1件は、祝日に回った燃やすごみの日 (薄い水色のマス) を読み落として「収集なし」と答えたもの。
  Opus でも、女川町が年度の途中 (10月) に変えた出し方は拾えず、4月に印刷された暦の分け方を答えた。
  公式の資料だけでは住所から地区が決まらない所もある (村上市の村上地域、宮崎市の清武、東海村の舟石川など)
- **2つの実験から見えた gomisute-gps の役目**: 最上位のモデルなら PDF でも正しく読めるので、「AI より正確」は売りにならない。
  そこで、**Opus のエージェント2人に公式の資料を別々に読ませ、一致したものだけをデータにして (この実験の正解づくりと同じ作り方)、
  軽いモデルやアプリに1回の問い合わせで安く配る**。データには有効期間と出典の日付・ハッシュを持たせて、年度途中の変更を監視する。
  住所と地区の対応表がウェブに無い所は、自治体から得てデータにする

### 6. LLM が「確かな答え」として使う場所: MCP サーバー ([docs/mcp-tool.md](docs/mcp-tool.md)、計測は [docs/mcp-bench.md](docs/mcp-bench.md))
2つの比較実験を受けて、gomisute-gps の役目を **LLM が1回の問い合わせで出典つきの確かな答えを得る場所** に絞った。

- [`mcp_server.py`](mcp_server.py): 標準入出力の MCP サーバー ([`.mcp.json`](.mcp.json))。ツールは3つ:
  住所で引く `garbage_collection_by_address` (金沢市・女川町)、緯度経度で引く `garbage_collection_by_location` (金沢市)、
  日付で分け方を引く `garbage_sorting` (女川町)。既定は答えに要る項目だけの要約 JSON (収集日は1回 約3千文字)
- **住所の文字列をそのまま区域表の行に当てる** (「笠舞2-29-5」「福久町ロ21番地」など。読み方は [`kzaddress.py`](kzaddress.py))。
  読んだ番号が国土地理院・ABR の住所データに実在するかも確かめる。地理院の住居表示住所 2,000件と ABR の地番 2,000件を、
  書き方を変えて約3万通り (漢数字・「N番地M」・「29 5」のような空白区切り・郵便番号や部屋番号つき・いろいろなダッシュ・市町村名なし・
  丁目や小字を落とした形・町名だけなど) 解析し直した ([bench/eval_address.py](bench/eval_address.py)): **確定 23,769件のうち誤り 0**。
  残りは候補を返して聞き返す (3,873件) か確定しない (2,937件)。丁目・小字を落とした形や町名だけは、読み方で地区が変わるなら確定しない
  (「泉野出町3-16」は 3丁目16番 とも 3番16号 とも X丁目3番16号 とも読める)。市町村名が無く、同じ町名がほかの市町村にもある住所
  (押野2丁目は野々市市にもある) も確定しない。独立した検証役が見つけた誤確定 (空白区切りの番号をつなげて読む、など) は直して評価に加えた
- **女川町**: カレンダーが PDF だけの町のデータを、Opus のエージェント2人の独立した読みで作った ([docs/onagawa-data.md](docs/onagawa-data.md))。
  日付のマス 324 (日付 742件) は2人の読みが全部一致。比較実験 2 の別の正解 6問とも一致。10月1日に変わった分け方は有効期間つきで、
  10月1日より後の日の答えには「カレンダーの見出しは4月印刷のまま。今の出し方は…」という注 (`label_note`) を付ける
- **公式ページの変更監視** ([`monitor.py`](monitor.py)): 元にしたページが変わったら、作り直して確かめるまで確かな答えとして返さない。
  MCP サーバーは、起動したときと動いている間 (1時間ごとに見て)、確認が 24時間より古ければ自分で取り直す (約6秒。ネットにつながらなければ前の結果のまま)。
  確認が 7日より古い・無いと、答えは `answerable=false` (「念のため公式ページでも確かめて」) になる
- **計測** (詳しくは [docs/mcp-bench.md](docs/mcp-bench.md)): 同じ AI (Claude Opus 5.5) に同じ質問をして、gomisute-gps を使わせた場合と
  ウェブ検索だけの場合を比べた (`claude -p`。答えた方式を伏せて採点)

  | | gomisute-gps を使う | ウェブ検索だけ |
  |---|---|---|
  | **費用** (1問あたり、58問の平均) | **約 $0.04** (約7円) | 約 $0.24 (約36円) |
  | **時間** (1問あたり、58問の平均) | **約15秒** | 約2分15秒 |
  | **正確さ**: 金沢 28問 | **28問とも正しい** | 27問 (1月だけの特別な収集日を外した) |
  | **正確さ**: 女川町 10問 (カレンダーが PDF だけ) | **10問とも正しい** | 3問 (PDF を読めず日付の 6問に答えられない。分け方の 1問は誤り) |
  | **正確さ**: 緯度経度だけ・地区の境目 20問 | **答えを出した 8問はすべて正しい**。12問は「位置だけでは決められない」と住所を聞き返した | 15問で答えを出し (うち 4問は「たぶん」と断り付き)、**3問は誤り** (隣の地区と取り違えた 2問、カレンダーの読み違い 1問)。5問は聞き返した |
  | **誤った答えを出した数** (58問) | **0問** | 5問 |
  | 付随して答えた情報の誤り | **0件** | 16件 |

  **費用は約5分の1、時間は約9分の1。gomisute-gps を使った AI は、58問で一度も誤った答えを出さなかった** (決められないときは住所を聞き返した)。
  ウェブ検索だけの AI は 5問で誤った答えを出した。カレンダーが読みやすい金沢の住所の問いでは正確さはほぼ同じで、差が出たのは
  1月だけの特別な収集日、PDF しかない町、年度の途中で変わった分け方、地区の境目の緯度経度 (円は 1ドル=150円で換算)。検証の途中では gomisute-gps 側の誤り
  (年内最後の収集日を品目でまとめていた、空白で区切った番地をつなげて読んでいた、など) も見つかり、直した

## 先行例: 5374 (ゴミナシ) との違い

金沢には 2013年から、Code for Kanazawa の [5374 (ゴミナシ)](https://kanazawa.5374.jp/) がある
([オープンソース](https://github.com/codeforkanazawa-org/5374)、MPL。fork は 579 あり、各地の版が作られた)。
「いつ、どのごみが収集されるか」をシンプルに見せる、市民がつくった先行例。gomisute-gps は、その次に要るものとして次を足した。

| | 5374 (金沢版) | gomisute-gps |
|---|---|---|
| 使う人 | 人がアプリで見る | LLM が MCP で引く (人のアプリからも使える) |
| 地区の決め方 | 利用者が地域を一覧から選ぶ | 住所・緯度経度から、市の区域表の行 (街区・番地まで) で決める。決められなければ候補を返して聞き返す |
| 収集日 | 地区ごとの曜日の規則 (例: 第3金曜日)。71地区 × 4品目。年末年始は休止期間のファイルから、後の収集日を1週ずらして計算する | 公式カレンダーの日付そのもの (71地区 × 5品目。第5週のプラスチック資源も) |
| 変更への対応 | 有志が更新。2026-10-18 に確認した時点では、データの最終更新は 2025-10-31 で、年末年始の休止期間は前年度 (2025/12/31〜2026/01/04) のまま | 元の公式ページの変更を監視し (MCP サーバーが1日1回確かめる)、変わったら確かな答えとして返さない |
| 対象 | fork した各地域 | 石川県金沢市・宮城県女川町 (2026年度) |

5374 の考え方 (曜日の規則 + 年末年始の休止で1週ずらす) は正しく、休止期間を今年度 (2026/12/31〜2027/01/03) にすれば、
2026年度の金沢の燃やさないごみ・資源・びんの日付は、gomisute-gps のデータとすべて一致する (検証役が 5374 の計算方法で確かめた)。
ただ、写したデータは更新が遅れるとずれる。計測 ([docs/mcp-bench.md](docs/mcp-bench.md)) では、ウェブ検索だけの AI が 5374 の曜日の規則と市のカレンダーを見て、
2027年1月15日 (田上地区) を燃やさないごみと答えて外した (正しくは資源。年末年始の休みで、1月は収集日が1週ずれる)。
gomisute-gps は、元の公式カレンダーの日付をそのまま持ち、その元のページが変わったかを監視する。

## スキーマ
### 収集区域と収集日 (v0.1)
- `zone`: zone_id, muni_code, members (町丁目コード), exceptions[], geom (MultiPolygon), confidence, source{url, fetched_at, hash}
- `schedule`: zone_id, category, rule_kind (`rrule` | `segments` | `explicit`), rrule, exdates, rdates, valid_from/to, source
- API 案: `GET /resolve?lat&lng&date` → zone_id, confidence, today[], tomorrow[] (confidence < 0.7 なら境界候補を返して利用者に選ばせる)
- 経路: gps2city (緯度経度 → lg_code・区) → 収集地区タイル → 境界までの距離で confidence

### 町名の正規化: address-normalize (v0.2 設計、[docs/address-normalize-schema.md](docs/address-normalize-schema.md))
自治体の資料に書かれた町名 (旧町名を含む) を現行の町字 ID に寄せる別 Worker (Cloudflare D1)。

- 町名をキーにせず、**町字の実体・表記・変更イベント・土地の移転**を分けて持つ (段階的な消滅・中間町名・復活に対応)
- 有効期間の境界は lo / hi / best の幅で持ち、「大半が移った日」と「名前が最後に消えた日」を分ける
- すべての事実に確信度・反証検証の結果・出典 (同じ元リスト由来の資料は1票) を付ける
- 照合キーは canon (同一視してよい) と fold (ノ/の など衝突しうる) の2段。fold で複数に当たったら自動で選ばない
- 設計は方針の違う3案を Claude に独立に作らせ、審査役が採点・統合 (16表、[DDL](docs/address-normalize-schema.sql))。
  全国 ABR 749,603 行 (296MB) と金沢の10ケースで検証済み ([prototypes/address-normalize/](prototypes/address-normalize/))

## 再現手順

Python 3.11+ / pandas / geopandas / shapely 2 / python-dateutil

```bash
# 金沢
python fetch.py https://www4.city.kanazawa.lg.jp/soshikikarasagasu/gomigenryosuishinka/gyomuannai/1/3/2/20102.html data/kanazawa_rules.html
python fetch_geo.py 17201          # 国勢調査2020 小地域
python kz_tables.py && python kz_rules.py
python split_blocks.py             # --holdout で 20% 点ホールドアウト精度 → out/kanazawa_holdout.json
# 旧町名の検証
python fetch_abr.py 172014 --all   # ABR (町字・地番・住居表示)
for y in 2000 2005 2010 2015; do python fetch_geo.py 17201 $y; done
python abr_check.py && python census_lineage.py
# 収集日と「緯度経度 → 今日のごみ」
python kz_calendar.py              # カレンダーのページを取得 → out/kanazawa_schedules.json
python resolve.py 36.481532 136.703003 2026-10-20   # --offline で gps2city を呼ばない
python split_blocks.py --holdout && python eval_resolve.py                       # 完全ホールドアウト
for s in 314 1 2; do python split_blocks.py --holdout-blocks --seed $s; done
python eval_resolve.py --mode blocks --seed 314,1,2                                # 街区ホールドアウト (3シードの合計)
python eval_resolve.py --mode parcels                                              # 地番ホールドアウト
python eval_resolve.py --mode parcels_split                                        # 地区が分かれる町の地番 (位置の無い地番)
python eval_resolve.py --jitter 3000,10,10                                         # GPS のずれ
python eval_resolve.py --jitter 3000,5,30 --accuracy                               # 30m 以内のずれ、accuracy_m を渡す
python eval_resolve.py --mode parcels_koaza                                        # 小字ホールドアウト
python eval_resolve.py --mode parcels --seed 7 --pnear 30,50,80                    # 地番の 80m を決めた別シード
for a in 20 30 50; do python eval_resolve.py --gauss 3000,5,$a,0.68; done           # 端末の精度どおりの誤差 (Android 式)
for a in 30 50; do python eval_resolve.py --gauss 3000,5,$a,0.95; done
python eval_resolve.py --gauss 3000,5,30,0.68 --no-accuracy
python eval_resolve.py --jitter 3000,5,50 --accuracy
# LLM 向けの MCP サーバーと、女川町・変更監視
python mcp_server.py                 # 標準入出力の MCP サーバー (.mcp.json から起動される)
python resolve.py --address 金沢市笠舞2丁目29番5号 2026-10-20
python build_onagawa.py <読み取りワークフローの結果.json> && python onagawa.py 浦宿浜 2026-12-22
python monitor.py --record           # データを作り直した直後だけ: 元にした公式ページの今の内容を記録する
python monitor.py                    # 記録と比べる (変わったページに基づく答えは確定しない)。MCP サーバーを使うなら自動で動くので不要
                                     # (サーバーの自動確認を止めるときは GOMISUTE_AUTO_MONITOR=0)
python bench/cli_bench.py mcp && python bench/cli_bench.py web --jobs 4   # 計測: claude CLI に MCP だけ / ウェブだけで同じ質問をする
python bench/eval_address.py         # 住所の書き方を変えて約3万通り解析し直す
```

地理院 住居表示住所 (`data/gsi_jukyo_17201.zip`, 2025-07-31版) は [国土地理院](https://www.gsi.go.jp/) から手動取得し `geo_peek.py` で CSV 化。
長野は [長野市 ごみ収集カレンダー オープンデータ](https://www.city.nagano.nagano.jp/n023500/contents/p006280.html) の `gomi_calendar_2026.zip`、世田谷は世田谷区オープンデータの「資源・ごみ収集日」CSV。

作者は **firemio** ([GitHub @firemio](https://github.com/firemio)) です。gomisute-gps は、同じ作者 firemio がこれまでに作った次の2つを土台にしています。

- [gps2city](https://github.com/firemio/gps2city) (作者: firemio) — 緯度経度 → 都道府県・市区町村 (国土数値情報 N03-2026 を 0.1° タイル化した Cloudflare Worker。能登半島地震の隆起でできた陸地も反映済み。[稼働中](https://gps2city.firemio.workers.dev/))。
  **Rust を WebAssembly にして Cloudflare Workers で動かし、全国のタイルを1本のパック (約23MB) にして Worker に埋め込んでいる**ので、初めて問い合わせる地点でも応答は中央値 11ms (外部読み込みだった頃は 250〜310ms、距離の誤差は最大 0.97m)。
  タイルの行政区域コードに検査数字を付けると ABR の市区町村コードと 1,898/1,905 件一致 (残り7件は所属未定地)。
  2026-10-17 から `POST /location` が `lg_code` (ABR と同じ6桁) と政令市の `ward` を返し、`/location2` は区ごとの境界距離 (`areas`) を返す。
  `/resolve` の入口 (GPS → 市区町村コード)、収集地区ポリゴンの配信 (同じタイル方式)、境界までの距離による確信度に使う
- [address2houmukyoku](https://address2houmukyoku.souzoku-tsumugiai.net/) (作者: firemio。サービスは公開中、ソースコードのリポジトリは非公開) — 住所 → 管轄法務局 (不動産登記・法人登記)。
  旧市町村→現市町村 1,801件 (1986〜2019) を address-normalize の市区町村層の下地にする。
  照合・正規化・12万件の郵便番号回帰検証・ハッシュ差分 LLM 抽出・特殊分割 (のうち/を除く/の一部) から得た知見は [docs/prior-art-address2houmukyoku.md](docs/prior-art-address2houmukyoku.md) にまとめた (ソースは非公開なのでコードは転載していない)
